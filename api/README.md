# SENTINEL-X API (prototype)

Prototype Node.js REST API with InfluxDB 3 Core persistence and a WebSocket event stream.
The REST API accepts alerts at `POST /api/v1/alerts` and lists them at
`GET /api/v1/alerts`. It accepts camera events at `POST /api/v1/events` and
returns the latest one at `GET /api/v1/events/latest`.

## Architecture

`src/services/alert-write-service.js` validates and creates alerts;
`src/services/alert-read-service.js` lists alerts; and
`src/services/event-service.js` validates, creates and reads the latest camera
event. These services receive the repository as a dependency, keeping
persistence details out of the services and allowing tests to inject a fake
repository. The HTTP server handles transport concerns and delegates to the
appropriate service.
InfluxDB connection settings and client APIs are isolated in
`src/persistence/influx-client.js`; alert points and event points are written
and queried by `src/persistence/alert-repository.influx.js`.
The point layout is documented in [INFLUXDB_SCHEMA.md](INFLUXDB_SCHEMA.md).
`createAlertServer` accepts an `alertRepository` option for injecting another
implementation and an `mqttCommandClient` option for command tests, which lets
tests run without InfluxDB or an MQTT broker.

## Requirements

- Node.js 20 or later
- npm
- InfluxDB 3 Core running locally or reachable over HTTP
- An MQTT broker (for example Mosquitto) to enable device commands

## Start locally

Run all commands in this README from the `api/` directory:

```sh
cd api
npm install
cp .env.example .env
# Set your InfluxDB token in .env
npm start
```

The API uses the InfluxDB 3 JavaScript client and writes with the native v3
write endpoint. `INFLUX_HOST` defaults to `http://127.0.0.1:8181`, the default
HTTP address for InfluxDB 3 Core. Provide an operator token in `INFLUX_TOKEN`
and an existing database name in `INFLUX_DATABASE`. For a local instance, the
InfluxDB CLI can create a database with
`influxdb3 create database alerts --token '<your-token>'`. Create an operator
token with `influxdb3 create token --admin` if the instance does not already
have one. Tokens should be kept out of source control.

The API loads `.env` automatically at startup. Set `INFLUX_TOKEN` in `.env`
before starting it; the template in `.env.example` lists the supported names.
Variables already exported in the environment take precedence over values in
`.env`.

To enable commands, configure `MQTT_URL` (for example
`mqtt://127.0.0.1:1883`). `MQTT_USERNAME` and `MQTT_PASSWORD` are optional when
the broker does not require credentials; `MQTT_CLIENT_ID` is optional and
otherwise generated by the API. If `MQTT_URL` is empty, alert and event routes
remain available but command requests return `503 mqtt_unavailable`. Set
`COMMAND_ACK_TIMEOUT_MS` to an integer from `1` to `60000`; it defaults to
`5000`.

By default, the API listens on `http://127.0.0.1:3000`, accepts alerts at
`POST /api/v1/alerts`, and stores each alert as a point in the configured
InfluxDB 3 database. Its point timestamp is the alert timestamp; `device_id` and a
generated UUID are tags, numeric measurements are written as
`measurement_<name>` fields, and `payload_json` preserves the complete alert.
The API waits for InfluxDB to flush each accepted alert before returning
success. WebSocket clients can connect to `ws://127.0.0.1:3000/ws` to receive
accepted alerts, events and command/device status updates.

Set `PORT` or `HOST` to override the server defaults. For example,
`HOST=0.0.0.0` makes the server reachable on the local network; do this only on
a trusted network because authentication is not implemented yet.

## Alert contract

### List alerts

`GET /api/v1/alerts` returns all alerts in reverse chronological order. The
response contains a `data` array with no pagination metadata:

```sh
curl -i 'http://127.0.0.1:3000/api/v1/alerts'
```

For a time-bounded query, `since` and `to` are required ISO 8601 UTC timestamps.
The range uses the measurement timestamp and returns all matching alerts:

```sh
curl -G 'http://127.0.0.1:3000/api/v1/alerts' \
  --data-urlencode 'since=2026-10-07T00:00:00.000Z' \
  --data-urlencode 'to=2026-10-07T12:00:00.000Z'
```

Both timestamps must be canonical ISO 8601 UTC values, `since` must not be
later than `to`. Without `since` and `to`, the API returns all alerts.

The response shape is:

```json
{
  "data": [
    {
      "id": "71a3eea1-6cdd-4af9-9aa1-bcbcc6d5268f",
      "timestamp": "2026-10-05T12:00:00.000Z",
      "device_id": "esp8266-demo",
      "measurements": { "temperature": 21.4, "humidity": 55.0 },
      "sensor_states": {},
      "received_at": "2026-10-05T12:00:01.000Z"
    }
  ]
}
```

Invalid query parameters return `400` with the standard API error shape.

### Create alerts

The request body must be JSON with:

- `timestamp`: required RFC 3339 timestamp with timezone
- `device_id`: required non-empty string, maximum 128 characters
- `measurements`: optional object whose values are finite numbers
- `sensor_states`: optional object whose values are booleans or short strings

Unknown top-level fields are rejected. Measurement and sensor-state names must
be 1-64 characters. Request bodies are limited to 16 KiB.

An alert can contain one or more numeric measurements. Use the names supplied
by the device; the API preserves them as-is. For devices that send one alert
per sensor, the following are examples:

| Sensor  | `measurements`            | `sensor_states` |
| ------- | ------------------------- | --------------- |
| DHT22   | `temperature`, `humidity` | empty           |
| MQ-2    | `gasRaw`                  | `gasDetected`   |
| PIR     | empty                     | `motion`        |
| HC-SR04 | `distanceCm`              | empty           |

Example:

```sh
curl -i http://127.0.0.1:3000/api/v1/alerts \
  -H 'content-type: application/json' \
  -d '{
    "timestamp": "2026-10-08T09:30:38.000Z",
    "device_id": "ESP-1",
    "measurements": {
      "temperature_c": 24.2,
      "humidity_pct": 51.7,
      "gas_raw": 122
    },
    "sensor_states": {
      "motion": true
    }
  }'
```

A successful request returns HTTP `201` with the saved alert, including its
UUID `id` and server-side `received_at` timestamp. Invalid JSON returns
`400`; invalid fields return `422`; unsupported content types return `415`;
oversized bodies return `413`. Errors use the shape
`{"error":{"code":"...","message":"...","details":[]}}` (details are present
for validation errors).

Each accepted alert is broadcast to connected WebSocket clients as:

```json
{
  "type": "alert.created",
  "data": {
    "id": 1,
    "timestamp": "2026-10-05T12:00:00.000Z",
    "device_id": "esp8266-demo",
    "measurements": { "temperature": 21.4, "humidity": 55 },
    "sensor_states": {},
    "received_at": "2026-10-05T12:00:01.000Z"
  }
}
```

## Event contract

The vision dashboard records one event when a person first appears in a
polling response after a period with no detected person. Further positive polls
do not create additional events; a poll with no detections rearms recording.
When the vision service is unavailable, the dashboard does not treat that as a
confirmed absence. Since the dashboard polls approximately once per second, the
event timestamp represents when the dashboard first observes the presence,
not the precise YOLO frame time.

Create an event with `POST /api/v1/events`:

```sh
curl -i http://127.0.0.1:3000/api/v1/events \
  -H 'content-type: application/json' \
  -d '{
    "timestamp": "2026-10-08T18:30:00.000Z",
    "source_type": "camera",
    "source_id": "CAM-ENT-03"
  }'
```

`timestamp` must be an RFC 3339 timestamp with timezone. `source_type` must be
`camera`; `source_id` is a 1-128 character identifier containing letters,
numbers, dots, underscores or hyphens. Unknown fields, including image data,
are rejected. Successful requests return HTTP `201` with an API-generated
event UUID and `received_at`. Each point is persisted in the InfluxDB
`events` measurement and broadcast as `event.created`.

`GET /api/v1/events/latest` returns the latest persisted event, or
`{"data":null}` when none has been recorded. The dashboard uses this endpoint
to populate the “Dernier événement” card after loading.

## Device command contract

The dashboard sends commands to the API; it does not connect directly to MQTT
or to ESP8266 GPIO pins. The API only accepts these actions:

- `buzzer.trigger`: the API always sets `duration_ms` to `5000`. The caller
  cannot choose a longer duration.
- `leds.test`: ask the ESP8266 to test its status LEDs.
- `leds.auto`: ask the ESP8266 to return its status LEDs to automatic mode.

Create one command at a time:

```sh
curl -i http://127.0.0.1:3000/api/v1/commands \
  -H 'content-type: application/json' \
  -d '{
    "device_id": "esp8266-demo",
    "action": "buzzer.trigger"
  }'
```

The API validates the body, generates `command_id`, and returns `202` with
`status: "pending"` after the MQTT broker acknowledges publication. That
response confirms delivery to the broker, not physical execution:

```json
{
  "data": {
    "command_id": "71a3eea1-6cdd-4af9-9aa1-bcbcc6d5268f",
    "device_id": "esp8266-demo",
    "action": "buzzer.trigger",
    "status": "pending",
    "created_at": "2026-10-06T12:00:00.000Z",
    "updated_at": "2026-10-06T12:00:00.000Z"
  }
}
```

The ESP8266 must acknowledge the command before
`COMMAND_ACK_TIMEOUT_MS` expires. The API tracks `completed`, `failed`, or
`unconfirmed` and emits each acknowledgement/timeout on the existing WebSocket
as `{"type":"command.updated","data":{...}}`. `unconfirmed` means the API did
not receive an acknowledgement; it does not prove that the action did not
happen. Retrieve a command's current state after reconnecting with
`GET /api/v1/commands/{command_id}`. Unknown or expired command IDs return
`404`.

The MQTT wire contract uses QoS 1 and these topics:

| Direction      | Topic                                            | Payload                                                                                         |
| -------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| API to ESP8266 | `sentinel-x/devices/{device_id}/commands`        | `{"command_id":"…","device_id":"esp8266-demo","action":"buzzer.trigger","duration_ms":5000}`    |
| ESP8266 to API | `sentinel-x/devices/{device_id}/command-results` | `{"command_id":"…","status":"completed"}` or `{"command_id":"…","status":"failed","error":"…"}` |
| ESP8266 to API | `sentinel-x/devices/{device_id}/status`          | `{"online":true}` or `{"online":false}`                                                         |

The API subscribes to command results and device status at startup. The device
status topic should be retained and the ESP8266 should configure an MQTT Last
Will payload of `{"online":false}`. Query a device with
`GET /api/v1/devices/{device_id}/status`; until the API receives a status
message, it returns `status: "unknown"`. The response also reports whether the
API itself is currently connected to the broker.

The API retains up to 500 recent command states in memory only. A server
restart loses them, and older terminal commands may be evicted; command state
is not written to InfluxDB. Invalid command bodies return `422`, an unavailable
or disconnected broker returns `503`, and unsupported HTTP methods return
`405`.

This prototype binds to localhost by default and does not implement client
authentication or TLS. Before exposing it beyond a trusted local network, add
authentication and configure HTTPS/WSS at the deployment or reverse-proxy
layer; the application does not claim to provide encryption itself.

## Send sample alerts

Start the server in one terminal, then send the sample alerts from
`test/fixtures/alerts.json` in another. The fixture includes an alert adapted
from a real database row; database-generated `alert_id` and `received_at`
values are omitted because the API creates these itself.

```sh
npm run send:alerts
```

The script posts each alert to `http://127.0.0.1:3000/api/v1/alerts` and prints
the ID returned by the API. Set `API_BASE_URL` to target another server:

```sh
API_BASE_URL=http://127.0.0.1:3001 npm run send:alerts
```

## Send sample events

With the API running and InfluxDB configured, send the sample camera events:

```sh
npm run send:events
```

The script reads `test/fixtures/events.json`, shifts its sample timestamps to
the current time while preserving their intervals, posts each event to
`POST /api/v1/events`, and queries `GET /api/v1/events/latest`. It prints the
saved IDs and the latest event returned by the API. To target another API
instance, set `API_BASE_URL`:

```sh
API_BASE_URL=http://127.0.0.1:3001 npm run send:events
```

Reload the dashboard after sending the dataset to display the latest persisted
event in its **Dernier événement** card.

To inspect saved rows with the InfluxDB 3 CLI, run:

```sh
influxdb3 query \
  --database alerts \
  --token '<your-influxdb3-token>' \
  'SELECT * FROM alerts ORDER BY time DESC LIMIT 10'
```
